# 登录角色锁定与体验修复设计

## 背景与目标

当前产品已经支持“提升自己”（`candidate`）和“判断他人”（`recruiter`）两种分析模式，但登录页没有角色选择，登录后的顶部导航允许随时切换模式。Candidate 页面还有外部 SVG 图标失效、岗位与 JD 输入框尺寸不一致，以及“本场表现结论”不够精简的问题。

本次迭代的目标是：让用户在登录或注册前选择角色，并在本次登录生命周期内锁定该角色；所有业务入口和历史报告只展示该角色内容；修复外部图标依赖、Candidate 表单对齐和结论结构；同时维护一份独立的未来风险与升级清单。

## 范围

本次包含：

- 登录与注册页增加“提升自己 / 判断他人”紧凑分段选择。
- 登录成功后锁定所选角色，删除桌面端和移动端顶部模式切换。
- 对工作台、历史、报告详情、首页入口和兼容路由执行角色一致性校验。
- 将 4 处外部 TOS SVG 图标替换为随应用构建的 Lucide 图标。
- 将 Candidate 的“目标职位名称”和“JD（选填）”输入区域改为等宽、等高。
- 将 Candidate 新报告的“本场表现结论”约束为三个结构化段落。
- 新增 `docs/未来需迭代内容.md`，记录强化版 A 的风险和升级为服务端 token 绑定角色的条件。
- 同步架构、交接与测试说明。

本次不包含：

- 不修改数据库 schema，不新增 `tokens.analysis_mode`。
- 不把角色变成账号永久属性。
- 不重写旧报告内容。
- 不重构密码哈希、token 过期、限流或管理员初始化机制，只在未来迭代文档中记录。
- 不执行生产部署。

## 核心决策：强化版 A

角色锁定是产品会话规则，不是服务端授权边界。它用于防止普通用户误切模式、混看历史或从产品路由进入另一角色；它不能阻止同一账号的用户修改浏览器存储或手工构造 API 请求访问本人另一模式的数据。

角色与当前本地登录状态使用相同生命周期。新增 `evalbar_auth_mode`，与 `auth_token`、`auth_user` 一起存放在 `localStorage`：登录或注册成功时写入，退出时清除。最终登录角色不放在 `sessionStorage`，避免浏览器关闭后 token 仍存在但角色丢失。

恢复登录状态时必须同时存在合法 token、用户和角色。任一项缺失或角色非法时，前端按失败关闭处理：清除本地认证状态并回到登录页，不再回退到最近模式或默认 `recruiter`。跨标签页检测到 token、用户或角色发生变化时，当前页面清除会话并要求重新登录。

## 登录与首页流程

登录页采用已确认的紧凑分段布局：

- 选项为“提升自己”和“判断他人”，附带简短任务说明。
- 主按钮固定显示“登录”；注册状态下保持现有“注册”文案。
- 首页角色入口先记录登录前意图，再进入 `/login`；登录页用该意图预选角色。
- 用户在提交登录或注册前可以更改预选角色。
- 登录成功后，提交时选择的角色成为唯一锁定角色，登录前路径参数不再具有决定权。

已登录用户访问首页时：

- 当前角色入口进入对应工作台。
- 另一角色入口不改变角色，显示“退出登录后可重新选择角色”的提示。
- 已登录访问 `/login` 时直接进入锁定角色工作台。

## 路由与页面隔离

认证上下文对外提供锁定角色，业务页面不再从 `getRecentMode()` 推断当前模式。

- `/app` 与 `/history` 根据锁定角色重定向。
- `/app/:mode` 与 `/history/:mode` 的参数必须等于锁定角色；不一致时重定向到当前角色对应页面。
- Logo、“新建分析”“历史记录”、返回、新建报告和重试操作全部使用锁定角色。
- 顶部导航的桌面和移动角色选择器全部删除。
- `/report/:id` 获取报告后比较 `report.analysisMode` 与锁定角色；不一致时不渲染报告，返回当前角色历史页并显示说明。
- 页面内 `analysisState` 在登录、退出或认证失效时清空，避免残留上一登录角色的数据。

管理员权限继续由服务端 `isAdmin` 决定。管理员后台可切换两套 Prompt；管理员自己的新建分析和历史页面仍遵守锁定角色。

## 历史与接口使用

前端历史页只用锁定角色请求 `/api/reports?analysisMode=<lockedMode>`。分析请求的 `analysisMode` 也由锁定角色与当前表单共同约束，避免普通页面状态产生不一致请求。

服务端现有的用户所有权校验保持不变：普通用户只能访问自己的报告，管理员按既有规则访问管理接口。当前迭代不把角色写入 token，因此手工 API 调用仍可能访问同一账号的另一模式；这一边界必须写入 `docs/未来需迭代内容.md`，不得把强化版 A 描述为服务端安全隔离。

## 图标修复

当前损坏来源是 4 处外部 TOS SVG：

- 首页“提升自己”角色图标。
- 首页“判断他人”角色图标。
- Candidate 简历上传图标。
- Candidate 面试记录上传图标。

删除对应 URL 常量和 `<img>`，改用 `lucide-react` 中语义匹配的本地图标。图标继续遵守现有 `components/ui.tsx` 的品牌色、尺寸和容器规则，不新增图标库或强调色。

静态测试需覆盖相关产品文件，禁止重新出现这些外部图标 URL 或远程产品图标 `<img>`。

## Candidate 表单对齐

“目标职位名称”和“JD（选填）”在桌面端继续并排、移动端继续上下排列。两个输入区域统一为固定 `112px` 高度，并使用相同边框、圆角、内边距和 focus 样式。

- 职位名称仍是必填短文本，使用不可拖动的文本输入区域。
- JD 允许多行输入，但关闭手动 resize，避免两侧重新失去对齐。
- 校验逻辑、字段名称和 API 数据结构不变。

## Candidate 报告结论契约

新生成报告的 `## 本场表现结论` 固定包含三个独立 Markdown 段落：

1. `**一句话总结：**` 用一句话概括整体表现，不给分、不预测录用。
2. `**本场重点：**` 明确写出“值得保留的做法 X 项、核心改进问题 Y 项”，并点出最优先改进问题。
3. `**下次准备：**` 用一句话概括下一次面试最需要准备的内容。

第二段数量必须与后续“值得保留的做法”和“最需要改进的核心问题”的实际条目一致。证据不足时允许数量少于默认值，但不得凑数。

`candidate_system_prompt` 已有数据库版本，单纯修改默认 Prompt 无法影响现有环境。因此采用无 schema 变更的兼容方案：

- 在 `services/candidatePrompt.js` 中定义带版本标记的 Candidate 结论输出契约。
- 新默认 Prompt 直接包含该契约。
- 模型调用前通过组合函数检查当前数据库 Prompt 是否包含该版本标记；缺失时追加契约，存在时不重复追加。
- 该契约作为产品稳定输出要求，不允许管理员误删后导致格式退化；管理员仍可编辑其余 Candidate Prompt 内容。
- 旧报告不做转换，继续按原 Markdown 渲染。

## 未来迭代文档

新增 `docs/未来需迭代内容.md`，作为持续维护的风险登记表。每项包含状态、优先级、当前风险、现有缓解、升级触发条件、目标方案和验收标准。

首批记录内容：

- 强化版 A 的客户端角色值可修改、手工 API 可绕过、旧链接可访问本人另一模式报告。
- 用户量、企业客户、审计或合规要求上升时，升级为服务端 token 绑定角色。
- 目标 B 方案：登录/注册提交角色，`tokens.analysis_mode` 持久化，认证中间件返回角色，分析、列表、详情、附件、删除和反馈接口统一校验。
- 密码使用无盐 SHA-256、token 无过期、本地存储 token、登录无明显限流、首用户自动成为管理员等现有认证风险。

`docs/architecture.md` 更新当前角色会话流和强化版 A 的能力边界；`docs/handoff.md` 记录本次交付、验证结果和未来文档入口。

## 错误处理

- 登录前角色值非法：回退到公开默认选项 `recruiter`，用户仍可在提交前选择。
- 已登录角色值缺失或非法：清除本地认证状态并回到登录页，不自动猜测。
- 路由模式与锁定角色不一致：重定向到锁定角色的同类页面。
- 报告模式不一致：不渲染内容，回到锁定角色历史并显示说明。
- 外部图标不再参与运行时加载，因此不需要图标网络错误兜底。
- Candidate 输出未完全遵守三段契约时，沿用现有容错 Markdown 渲染；不在前端伪造摘要或数量。

## 测试与验收

自动化测试至少覆盖：

- 登录角色的合法值、持久化、恢复和退出清理。
- token、用户或角色缺失时失败关闭。
- 登录前预选角色不会覆盖提交时选择。
- `/app`、`/history`、显式模式路由和报告模式不一致时的目标路径。
- Candidate Prompt 契约对旧数据库 Prompt 追加一次，对新默认 Prompt 不重复追加。
- Candidate 结论契约包含三段标签、数量一致要求和一句话限制。
- 产品源文件不再引用已失效的外部 SVG。
- Candidate 两个输入区域具有一致高度和禁止 resize 的样式。

代码完成后运行：

```bash
npm test
npm run build
```

浏览器验收覆盖桌面端和移动端：登录预选与修改、登录后无角色切换、直接访问另一模式路由、当前角色历史、另一模式报告拦截、首页入口提示、4 处图标显示、Candidate 输入框对齐。

## 发布边界

本次设计和本地实现不包含生产发布。生产部署前需要重新确认授权，并按项目运行手册执行完整 `data/` 备份、构建、PM2 重启和冒烟检查。由于当前方案不修改 schema，不需要数据库迁移。
